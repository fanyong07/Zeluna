# Zeluna 外部弹幕源接入调研（Bilibili / 腾讯视频 / 弹弹play）

- 调研日期：2026-08-23
- 调研范围：官方开放平台、官方 API 文档、官方使用约定与当前仓库实现
- 性质：接入决策与后续实现依据；本轮不修改业务代码

## 1. 结论

| 来源 | 截至调研日的官方接入状态 | Zeluna 建议 |
| --- | --- | --- |
| 弹弹play | 有面向第三方的“开放弹幕网络 API v2”，覆盖识别、搜索、匹配和弹幕读取 | **第一优先级正式接入**，凭证放 Zeluna 后端，客户端只访问自有 API |
| Bilibili | 官方开放平台未公开普通点播视频/番剧的弹幕正文读取能力；公开能力只有稿件弹幕数量等数据，直播间发弹幕还是限定商务能力 | **不得把网页内部接口当正式数据源**；需要正文只能先取得 Bilibili 书面商务/数据授权 |
| 腾讯视频 | 腾讯视频官方开放平台页面明确显示“系统已停止运营”；未找到仍受支持的腾讯视频弹幕正文开放 API | **当前不直接接入**；如需腾讯视频原始弹幕，只能联系官方取得新的合作接口与授权 |

推荐产品方案是：保留 Zeluna 自建社区弹幕，以弹弹play作为唯一正式外部弹幕源；Bilibili 和腾讯视频先显示为“未获得官方开放接口”，不要用 Cookie、网页签名、私有接口或抓包结果绕过。

上述 Bilibili 结论来自其官方平台能力目录、“文档中未列出的功能”说明、点播稿件数据文档和直播弹幕文档；腾讯结论来自腾讯视频开放平台关停公告；弹弹play结论来自其官方接入指南、Swagger 与配额公告。[B1][B2][B3][B4][T1][D1][D2][D3]

## 2. 范围与关键规则

本方案做：

- 通过获得授权的官方 API 读取弹幕。
- 建立作品/剧集到第三方 `episodeId` 的稳定映射。
- 统一转换时间、模式、颜色、正文和来源信息。
- 提供缓存、限流、错误降级、来源开关和匹配纠错。

本方案不做：

- 不逆向或调用网站未公开的搜索、剧集、弹幕分片接口。
- 不复制网页端 WBI、动态签名、设备指纹或其他风控算法。
- 不使用用户 Cookie、登录态、会员账号或浏览器会话批量取数。
- 不伪造 Bilibili/腾讯视频官方合作，不把弹弹play聚合结果标成两家官方直供。
- 不做弹幕数据库批量下载、长期镜像或商业转售。

## 3. Bilibili

### 3.1 直接回答

**有，Bilibili 确实有官方开发者/开放平台。** 但“有开放平台”不等于“公开开放全部站内数据”。截至 2026-08-23，其第一方公开文档能确认的弹幕相关能力应严格分成四件事：[B1][B2][B3][B4]

| 问题 | 第一方公开资料结论 |
| --- | --- |
| 是否存在官方开放平台 | **存在**，平台向机构、有开发能力的 UP 主、垂直行业企业和品牌服务商提供申请制能力。[B1] |
| 是否公开普通点播/番剧弹幕正文读取 | **没有在公开文档中开放**；未列出的数据需求应联系官方评估商务合作，不能自行使用网页内部接口代替。[B4] |
| 是否能读取点播稿件的弹幕数量 | **可以，但有范围限制**；获批 `ARC_DATA` 且取得稿件作者或联合投稿人授权后，单稿件数据会返回 `danmaku` 数量，不返回正文。[B2] |
| 是否有直播弹幕能力 | **有，但公开文档中的“直播间发送弹幕”是限定商务能力**，需先与商务运营沟通；它既不是普通开放权限，也不是点播弹幕正文读取。[B3] |

因此，对 Zeluna 的准确表述不是“Bilibili 没有开放平台”，而是：**Bilibili 有官方开放平台，但当前第一方公开能力不包含 Zeluna 所需的全站点播弹幕正文读取。**

### 3.2 官方资料能证明什么

Bilibili 开放平台主要面向机构、有开发能力的 UP 主、垂直行业企业和品牌服务商，并通过申请权限与用户授权提供开放能力。[B1]

官方“获取单个稿件数据”接口只返回播放数、弹幕数、评论数等统计值；其中 `danmaku` 是数量，不包含弹幕正文。它还要求 `ARC_DATA` 权限和稿件作者/联合投稿人的用户授权。[B2]

官方目录里的“直播间发送弹幕”明确是限定能力，要求事先与商务运营沟通；它不是点播弹幕读取接口。[B3]

官方“文档中未列出的功能”说明：未公开的数据或接口需求应邮件联系开放平台，由双方评估合作收益后决定；因此不能把 `api.bilibili.com` 域名下的网页内部接口自动视为开放 API。[B4]

官方运营规范还要求不得滥用接口、不得超出授权使用数据、不得泄露通过开放平台取得的数据，并禁止未经书面许可使用插件或外挂等第三方工具接入其服务或系统。[B5]

### 3.3 对 Zeluna 的实际结论

- **认证/签名**：只有取得正式开放平台应用、相应 Scope 和用户/商务授权后，才能按获批文档使用官方签名；不存在可用于公开读取全站点播弹幕正文的通用凭证方案。[B2][B4]
- **内容匹配**：官方未提供“任意外部片源标题/集数 → Bilibili 弹幕”的公开匹配流程。若将来获批，应只保存授权接口返回的官方内容 ID，并允许管理员或用户确认映射。
- **弹幕格式**：官方未公开普通点播弹幕正文的受支持第三方响应格式，因此 Zeluna 不能把 XML 或 protobuf 网页响应格式当成稳定合同。
- **频率限制**：由于没有公开的点播弹幕正文 API，也没有可适用于该用途的官方频率承诺；网页请求出现 412 等现象不能当作 API 配额规则。
- **商业边界**：未获得书面授权前，不应使用、缓存、再分发 Bilibili 点播弹幕正文。[B4][B5]

当前仓库 `lib/src/data/danmaku_repository.dart` 会调用 Bilibili 网页搜索、番剧详情和 `x/v1/dm/list.so`，并在客户端生成 WBI 参数。这只能算未公开网页接口的实验实现，不能作为正式发布所宣称的“Bilibili 官方弹幕接入”。后续业务实现应默认关闭或移除这条生产路径，直到取得书面授权。

## 4. 腾讯视频

### 4.1 官方资料能证明什么

腾讯视频官方开放平台 `https://v.qq.com/open/` 当前直接显示“系统已停止运营”，并给出 `v_open@tencent.com` 作为疑问联系邮箱。[T1]

在这一官方状态下，没有可供 Zeluna 依赖的、仍受支持的腾讯视频消费者平台弹幕正文读取文档。不能从“网站播放器能够显示弹幕”推导出第三方拥有数据读取权。

### 4.2 对 Zeluna 的实际结论

- **认证/签名**：没有仍公开受支持的腾讯视频弹幕正文第三方认证流程。
- **内容匹配**：没有公开的“腾讯视频节目/集 → 外部片源剧集”匹配合同。
- **弹幕格式与频率**：没有面向第三方公开承诺的正文格式和调用额度。
- **商业边界**：不要实现 `dm.video.qq.com` 等网页内部地址、网页 token、Cookie 或签名算法；若确实需要腾讯原始弹幕，应联系官方邮箱取得书面授权、接口文档、配额、缓存与展示规则后再开发。[T1]

如果弹弹play在 `withRelated=true` 的结果里返回了关联第三方弹幕，Zeluna 应将数据来源显示为“弹弹play聚合”，不能声称是腾讯视频官方直连。[D1][D2]

## 5. 弹弹play

### 5.1 申请与凭证

第三方需在弹弹play DevCenter 创建应用并申请 `AppId`、`AppSecret`。官方 API 基址是 `https://api.dandanplay.net`。[D1]

官方支持两种请求认证：

1. 签名模式：`X-AppId`、UTC 秒级 `X-Timestamp`、`X-Signature`。
2. 凭证模式：`X-AppId`、`X-AppSecret`。

签名算法是：

```text
base64(sha256(AppId + Timestamp + Path + AppSecret))
```

其中 `Path` 以 `/` 开头，不含协议、域名和查询参数，建议使用小写。官方推荐客户端使用签名模式，同时明确建议不要在客户端硬编码 `AppSecret`，开源客户端可由自建服务端转发并把密钥保存在服务端。[D1]

对 Zeluna 最稳妥的做法是：**AppSecret 只放 VPS 环境变量，由 Zeluna 后端签名或使用凭证模式；Flutter APK/Windows 包、用户设置、日志和 Git 仓库中都不出现共享密钥。**

### 5.2 内容匹配流程

官方提供两条流程：[D1][D2]

1. 本地文件优先调用 `POST /api/v2/match`，参数包括文件名、文件前 16MiB 的 MD5、文件大小、视频时长和匹配模式。
2. 网络播放或自动匹配失败时，调用 `GET /api/v2/search/episodes`；可按作品标题，也可按 TMDB ID、电影/剧集类型和集号搜索。结果不唯一时应让用户确认。

匹配成功后保存弹弹play `episodeId`。Zeluna 应保存稳定映射：

```text
subject_key + episode_key
  -> provider=dandanplay
  -> external_episode_id
  -> match_method(hash/tmdb/title/manual)
  -> user_confirmed
```

不应在每次播放时重新按标题猜测；用户纠正后的映射应优先使用。

### 5.3 弹幕拉取与格式

读取接口：[D2]

```text
GET /api/v2/comment/{episodeId}?from=0&withRelated=true&chConvert=1
```

官方说明该接口会以 HTTP 302 跳转到弹幕加速服务；实现时只应跟随 HTTPS、经过域名校验的跳转，并限制响应大小和超时。

响应核心字段：[D2]

- `cid`：弹幕 ID。
- `p`：`出现时间,模式,颜色,用户ID`。
- `m`：弹幕正文。
- 模式 `1` 为滚动、`4` 为底部、`5` 为顶部。
- `withRelated=true` 会合并关联第三方弹幕，是官方推荐的整合读取方式。

Zeluna 转换后应保留 `provider=dandanplay`、原始 `cid`、秒级时间、模式、RGB 颜色和文本，并按“时间 + 规范化文本”做显示层去重。

### 5.4 额度、缓存和商业边界

弹弹play文档没有公布统一固定的“每秒 N 次”限制。自 2026-06-25 起已启用按项目分层的每日/月度配额，具体额度由开发者后台显示；搜索和获取弹幕还会检测远超正常使用范围的调用，超量项目需联系白名单或升级层级。[D1][D3]

官方建议缓存：一般数据 2–6 小时；热门新番更新日 30–60 分钟；非当季内容 12–24 小时；老番 2–7 天。调用应由用户播放行为触发，不得批量抓取或下载数据库。[D1]

未经明确授权禁止商业使用，包括把弹幕作为收费功能、核心付费卖点或向第三方转售；商业化前应转入商业授权层。免费、非商业项目仍需按应用审核结果和分层额度执行。[D1][D3]

第三方若发送弹幕，应使用 `POST /api/v2/comment/{episodeId}/app`；不同应用的弹幕进入各自私有库。Zeluna 的首版建议只读，发送仍走自建社区弹幕，待确认账号、审核、举报和商业授权后再开放弹弹play写入。[D1][D2]

## 6. 推荐实现顺序

1. 把现有 `DanmakuRepository` 拆成“Zeluna 自建源 + 弹弹play官方源”两个正式 provider。
2. 在后端新增弹弹play适配器和剧集映射缓存；密钥只读环境变量。
3. 优先使用 TMDB ID + 类型 + 集号匹配，标题匹配作为备用，歧义结果交给用户确认。
4. 读取 `comment/{episodeId}`，安全处理 302，转换为现有 `DanmakuComment`。
5. 按官方建议缓存并增加项目配额监控；任一外部源失败不得影响播放和自建弹幕。
6. Bilibili、腾讯视频入口默认关闭并说明“暂无官方开放读取接口”。取得书面授权后再各自新增 provider。

建议数据流：

```text
Flutter 播放器
  -> Zeluna /api/v3/danmaku（统一结果）
     -> Zeluna 自建社区弹幕
     -> 弹弹play后端适配器（AppSecret仅在VPS）
```

后端外连必须使用专用客户端、域名白名单、HTTPS、私网地址阻断、超时、响应上限和重定向复验；不能做任意 URL 弹幕代理。

## 7. 验收标准

- APK、Windows 包、Git 历史和日志中找不到弹弹play `AppSecret`。
- 正常流程能完成“匹配 → 用户确认（如需要）→ 保存 episodeId → 拉取 → 转换 → 播放同步”。
- 匹配错误可纠正且纠正结果会持久化，不在每次播放时漂移。
- 302 只跳转到安全的 HTTPS 公网目标，响应大小与超时受限。
- 外部接口失败时，视频播放与 Zeluna 自建弹幕仍正常。
- 缓存和调用量符合弹弹play当前项目配额，不进行预抓取或批量镜像。
- 未授权版本不请求 Bilibili/腾讯视频网页内部弹幕接口，也不要求用户提供 Cookie。
- UI 准确标注“Zeluna”“弹弹play聚合”，不作官方合作暗示。

## 8. 待确认事项

1. 需要在弹弹play DevCenter 为 Zeluna 创建应用并确认审核层级、实际日/月配额及是否属于商业使用；这是账号与授权操作，应由项目所有者确认。
2. 如果 Zeluna 将来收费、加广告或把弹幕作为会员权益，必须先取得弹弹play商业授权。
3. Bilibili/腾讯视频是否值得发起商务合作，需要根据用户规模、调用量、展示方式和双方收益另行准备申请材料。
