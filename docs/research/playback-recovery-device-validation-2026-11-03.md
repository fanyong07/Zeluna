# 播放失败恢复与设备验证交接

## 背景与目标
用户实装后要求修复 TLS、超时和卡顿，并验证手机 Clash Meta 开关对照、实际滚动流畅度及 Windows 视频播放。用户禁止 Computer Use；本轮只使用代码、命令行、ADB 设备信息和 Flutter 集成测试，未使用桌面输入自动化。

## 已复现的问题与实现
1. 连续的媒体 TLS 失败只写日志，未触发恢复；首帧看门狗超时后还会重开同一 URL，导致重复等待。两次启动传输失败后结束该线路尝试；看门狗耗尽启动预算后直接寻找备用线路。
2. `playbackLineCanStartImmediately` 仅看服务器曾验证成功，忽略过期缓存和需要本机检查的标记。现在复用既有准入条件，过期结果不能跳过本机验证。
3. 自动换线按原始来源顺序挑选，可能在已有本机验证备用线路时仍逐条等待旧候选。恢复优先使用有效的本机验证结果，同组仍保留原有来源顺序。
4. 打开媒体的验证复用了资料清单查询的取消信号；取消后返回的原始候选仍可能进入解码器。现在验证由当前媒体打开操作拥有，退出、换集、暂停、手动操作均可取消；晚到或取消结果不能继续打开。
5. Windows 实播重现反复三四秒短缓冲：36 秒观察仅前进约19秒，但每次都未达到连续5秒停顿阈值。既有一秒检测器增加20秒有界观察窗口；至少3次缓冲、12秒观察和累计8秒低缓冲等待才恢复。单次短抖动、暂停、后台、拖动、启动等待及片尾不触发该判定。
6. 点播 HLS 的第一段或其密钥失效时，检查器会因后面的分片可访问而接受整条线路，但播放器仍从坏的第一段启动。点播现在要求首段及其密钥可读；直播仍允许在滚动窗口内检查最近分片。开始播放的检查不再等待可选的文件大小估算。
7. Windows 原生 FFmpeg 网络路径与 Dart 媒体检查不同，出现检查通过后解码器连接失败。Windows 现在复用 Android 已有的本机媒体通道，统一 TLS、域名解析和失败回报，保留严格证书校验、跨域敏感头移除和私网隔离。DASH、本地离线文件保持既有路径。
8. 后台检查把带有旧服务器测速的过期线路排除在并行队列之外，导致播放器逐条等待约10秒超时。过期服务器结果现在仍进入既有的最多4路并行检查，不另建调度器；先完成的可用候选立即发布。
9. 第五轮实播发现有效线路的媒体检查实际仅2秒，却在后台扫描队列等待约13秒。媒体检查总并发仍为4，后台最多使用3个，另1个保留给明确打开/刷新所用的 `forceRefresh` 检查；不会为了提速提高总网络并发。阻塞后台请求的回归测试验证当前播放仍可先完成。
10. 实体安卓复验后检查首帧等待，发现硬截止时间按轮询次数累加。UI线程忙时轮询晚到，实际截止也随之后移。回归测试阻塞事件循环直到硬截止以后，旧代码仍继续等待；修复为启动时独立安排硬截止定时器，取消、首帧、旧打开和销毁统一清理两个定时器。它不能让阻塞中的线程提前执行，但不会在恢复执行后继续累加已经过去的等待时间。

所有恢复继续遵守用户暂停意图、自动换线开关、账号隔离和媒体打开序号。没有关闭证书检查，没有更改 VPN、代理或放宽私网限制。上游证书故障不伪装成可用线路。

## 验证入口
- `test/player_pause_intent_regression_test.dart`：真实页面、取消/换线/播放器调用链；新增 TLS、超时和取消结果回归均先失败再修复。
- `test/playback_recovery_controller_test.dart`：重复短缓冲与单次短抖动对照。
- `test/playback_line_controller_test.dart`、`test/playback_line_display_test.dart`：本机验证优先与旧缓存准入。
- `test/rule_playback_resolver_test.dart`、`test/native_media_transport_test.dart`：首段/密钥失效、平台通道接入、私有凭据不转发到回环监听器及销毁关闭连接。页面状态回归使用显式测试传输替身，不依赖真实网络或开放端口。
- `integration_test/device_network_playback_test.dart`：真实后端资料、实际封面解码、真实列表滚动 FrameTiming、默认 PlayerPage 选线与原生视频帧；不注入媒体 URL。连续观察至少35秒，进度至少增加28秒；发生自动换线时记录被替换窗口，并要求新线路重新完成整个观察窗口，恢复总预算120秒。
- Android 性能测试必须传 `-PzelunaQaApplication=true`，仅 debug/profile 使用独立的 `app.anime.anime.qa`。正式 release 包名不变。测试不读取正常 App 的账号或本地存储。
- 性能测试不额外强制开启语义树，保留平台真实无障碍状态并把 `semantics_enabled` 写进帧耗时结果。Flutter `testWidgets` 默认强制开启语义树，会把测试开销混入普通使用性能；不应通过关闭用户无障碍设置来获得较好数字。
- Android 的完整测试结果读取 Flutter integration driver 的结构化响应，不依赖可能截断或漏收的 logcat 行。`flutter drive` 必须带 `--keep-app-running`，完成后只停止独立测试进程，防止默认卸载使两组 VPN 的应用 UID 发生变化。VPN 状态同时核对活动类型与当前连接，开启时必须验证 QA UID 在 VPN 覆盖范围内；仅看到配置里的 `Transports: VPN` 不能证明已连接。

## 已有证据与边界
具体计数、提交、包哈希和每轮结果保存在被忽略的 `.codex_tmp/playback-recovery-20261103`，最终审查后的交付证据写入 `output/`。保留失败记录，不将失败测试改名为通过。

- Windows 第一轮 profile 实播实际解码1920×1080，但持续播放断言失败，发现重复短缓冲；第二、三、四轮已经通过连续播放窗口。第四轮使用统一媒体通道：首帧55.9秒，随后36.5秒播放进度前进36.5秒，无缓冲停顿；该轮仍暴露后台跳过旧测速的慢启动问题，不能据此宣称启动已加速。滚动168帧，构建耗时p95为1.25ms，光栅耗时p95为7.64ms，6帧超过16.7ms，不宣称零卡顿。最终修复后的实播需单独凭据记录。
- 一加 Ace 2 Pro（PJA110，Android16，用户提供系统版本 `PJA110_16.0.5.1201(CN01C10P02)`）曾读取到安装版1.2.8，用户说明使用Clash Meta规则模式。再次连接后Windows能枚举设备，但USB标识读取与数据写入报系统错误31。未在这台手机安装测试包，未改驱动、注册表、用户App或VPN；该机实播仍未验证。
- 用户改接一加平板 OPD2407，实际读取 Android16 / `OPD2407_16.0.5.1001(CN01)`。在提交 `190ae9a5b8c00b937f9e5cdee8777f4fc0c39ecd` 的独立 profile 包上，关闭VPN首轮43.094秒首帧，1080p观察35.581秒、前进34.208秒、最长停顿1秒；Clash Meta规则模式首轮11.086秒首帧，观察35.688秒、前进35.667秒、无停顿。两组封面实际解码、详情均成功，开启组核实QA UID确实经过VPN。追加CPU采样轮首帧40.607秒，说明启动时间仍受线路波动影响，不能只选最快一轮宣称秒开。
- 上述平板初轮滚动测试被框架默认强制开启语义树，而设备系统无障碍为关闭。CPU采样证实帧内有显著语义更新开销；这些数字保留为旧测试条件的原始结果，不能当作普通使用流畅度的最终数字。修正测试条件和硬截止实现后的同提交双端实播、平板VPN两组结果仍需重新记录。
- 实体平板结果不等于一加Ace2Pro结果。没有用开发机代理或模拟器替代实体设备对照，也没有宣称所有来源均可播放。
- Windows profile 测试和最终发布 ZIP 的静态完整性核验分别记录，不能声称两者为同一二进制的操作验收。
